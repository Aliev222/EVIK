# Чат по заказу

Текстовый чат доступен только владельцу заказа и водителю, который **сейчас** назначен на него. Администратор не получает исключения. После отмены участники могут читать историю, но новые сообщения запрещены; после переназначения прежний водитель теряет и чтение, и realtime-доставку.

## HTTP

Все запросы требуют `Authorization: Bearer <access token>`.

- `GET /api/v1/orders/{orderID}/chat/messages?limit=50&before_id={messageID}` — сообщения по возрастанию `(created_at,id)`. `limit` по умолчанию 50, допустим 1–100; `0`, отрицательный, нечисловой и больше 100 дают `400`. При наличии следующей страницы `next_before_id` передаётся в следующий запрос. Неизвестный или принадлежащий другому заказу `before_id` даёт `400`.
- `POST /api/v1/orders/{orderID}/chat/messages`

```json
{"client_message_id":"01J...","text":"Буду через пять минут"}
```

Успешный ответ `201` означает, что сообщение сохранено. Повтор с тем же `client_message_id` того же отправителя возвращает то же серверное сообщение. Пустой текст и текст длиннее 1000 символов отклоняются; сервер ограничивает отправку до одного нового сообщения за 750 мс на отправителя.

## WebSocket `/ws/orders`

Используется то же авторизованное соединение, что и для заказов и геолокации. После подключения экран подписывается ровно один раз:

```json
{"type":"chat.subscribe","data":{"order_id":"order-123"}}
```

Сервер отвечает `chat.subscribed` или `chat.error`. При возврате из фона клиент заново подписывается и догружает HTTP-историю; объединение выполняется по серверному `message.id`.

Отправка через WS поддерживается наряду с HTTP:

```json
{"type":"chat.send","data":{"order_id":"order-123","client_message_id":"01J...","text":"Буду через пять минут"}}
```

`chat.ack` содержит сохранённое сообщение. Входящее для подписанного получателя приходит как стандартный event:

```json
{"type":"chat.message","order_id":"order-123","payload":{"message":{"id":"…","sender_id":"…","client_message_id":"…","text":"…","created_at":"…"}}}
```

Тексты сообщений и access tokens не попадают в технические логи.

Realtime использует Redis Pub/Sub и поэтому не является гарантированным каналом доставки: публикация — best-effort уведомление, а PostgreSQL — источник истины. HTTP и WS подтверждают сохранённое сообщение после записи; при ошибке публикации клиент восстанавливает пропущенные сообщения через историю после reconnect/resume. Повторная отправка того же `client_message_id` возвращает исходную запись без изменения текста.
