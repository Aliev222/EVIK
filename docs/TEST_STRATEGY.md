# Авро — Тест-стратегия и план полного покрытия

> Цель: покрыть тестами ВСЕ значимые сценарии — обычные, граничные и враждебные
> (то, что может случайно положить приложение). Плюс полный «рентген» приложения.
> Принцип: риск-ориентированно по пирамиде тестов, не тривиальные геттеры.
> Каждая значимая функция получает 3 класса сценариев: happy / edge / adversarial.
> Дата: август 2026.

---

## Пирамида (целевой баланс)
```
        E2E            мало, медленно, высокая уверенность (полный цикл заказа, диспетчеризация)
     Integration       средне (репозитории на живой Postgres, HTTP-слой)
   Unit / Widget       много, быстро (бизнес-логика, виджеты)
   Property / Fuzz     адверсариал-инпуты, арифметика денег, конкурентность
```

## КЛАСС «ADVERSARIAL» — что именно может положить приложение
Для каждого домена обязательно тестировать НЕ только happy path:
- **Числа/деньги**: 0, отрицательные, огромные (int64 overflow), копейки vs рубли, округление half-up, дробные км.
- **Строки**: пустые, очень длинные, Unicode/кириллица/эмодзи в адресах и именах, SQL-мета-символы (проверить параметризацию), null-байты.
- **Координаты**: за диапазоном (lat>90), NaN/Inf, (0,0), полюса, антимеридиан.
- **Конкурентность**: два действия одновременно (accept, payout, оплата, отмена) — ровно один победитель, без двойного списания.
- **Состояния**: действие в неверном статусе (оплатить отменённый, финализировать завершённый, принять чужой заказ).
- **Сеть/провайдер**: таймаут, 500, невалидный JSON от провайдера, дубль вебхука, поддельный вебхук.
- **Auth**: истёкший/поддельный/чужой токен, роль client дёргает admin-эндпоинт, отсутствующий заголовок.
- **Идемпотентность**: повтор запроса с тем же ключом не создаёт дубль (заказ, платёж, выплата, вебхук).
- **Пустые/отсутствующие данные**: заказ без водителя, водитель без кошелька, платёж без заказа.

## План покрытия по доменам (backend)

### 1. Деньги (высший приоритет)
- **pricing/calculate**: 3 цены за один запрос; дистанция 0/огромная; тип ТС невалидный; цена ≤0 → заказ заблокирован; ставка из platform_settings.
- **finalize_order**: серверная цена записывается всегда; число водителя вне допуска 1₽ → reject (inflated И underpriced); нет серверной цены → reject; финализация не-in_progress → reject; чужой водитель → reject.
- **confirm_payment**: cash → settlement+completed атомарно; card paid → completed; card не paid → confirmation_url; повтор → идемпотентно; rollback при сбое settlement.
- **payout**: резерв outstanding (2 параллельных > баланс → один); ApprovePayout проверяет баланс; failed не одобряем; CHECK≥0; MarkPayoutPaid; RejectPayout возвращает; minimumWithdrawal.
- **wallet/settlement**: split инвариант (price = driver_amount + commission_amount); комиссия 15% из settings, fallback; available/pending/debt раздельно; release pending; идемпотентность по ключу; параллельный кредит.
- **webhook**: дедуп (50 параллельных дублей → 1 обработка); поддельный IP; mid-tx failure rollback; retry after failure/success; верификация подписи.

### 2. Жизненный цикл заказа / стейт-машина
- Все валидные переходы (created→searching→accepted→arrived→in_progress→awaiting_payment→completed).
- Все ЗАПРЕЩЁННЫЕ переходы → ErrInvalidTransition (напр. completed→cancelled, searching→completed).
- Отмена на КАЖДОМ этапе: освобождает водителя, возвращает в пул, не двигает деньги (их ещё нет).
- no_driver_found; expansion (is_expanded) поиска.
- Идемпотентность создания (тот же ключ → тот же заказ; пустой ключ → новый).

### 3. Диспетчеризация / matching / офферы
- Один активный оффер на заказ; один активный на водителя (гонки).
- Accept: ровно один водитель выигрывает при гонке; занятый водитель → reject.
- **Блокировка водителя** (после фикса): заблокированный убран из пула, активный заказ переназначен/отменён по решению.
- Таймаут оффера; водитель офлайн; расширение зоны.

### 4. Auth / OTP / RBAC
- OTP: генерация, срок годности, потребление (нельзя дважды), неверный код.
- **Rate limiting OTP** (после фикса): N запросов/мин → 429.
- JWT: валидный/истёкший/поддельный; refresh-сессии.
- RBAC: client→admin эндпоинт = 403; driver→admin = 403; нет эскалации до admin.
- Верификация водителя: pending→approved/rejected; повторный approve отклонённого; коллизия write-path.

### 5. Гео / геокодирование / маршруты
- Reverse-geocode через backend: валидные lat/lng; вне диапазона → 400; not-found → 404; провайдер down → 502; rate-limit 1 req/s соблюдён.
- Прямой city-search (bbox); slug транслитерация кириллицы.
- Route preview; профили; пустой маршрут.

### 6. Admin (МИНИМАЛЬНО — админка на пересборку)
- Только зафиксировать найденные баги тестами-регрессами (orders.completed_at, moderation_audit_log), чтобы пересборка их не воскресила. Глубоко не покрывать — будет переписано.

## План покрытия (frontend)

### Виджет-тесты (по экранам)
- Клиент: главная (адрес/карта/состояния загрузки/ошибки), pickup/dropoff пикеры, выбор ТС/цены, трекинг статусов, оплата (cash/card), отзыв, история, профиль, кошелёк.
- Водитель: онбординг, загрузка документов, экран модерации (поллинг статуса), home (онлайн-тумблер), активный заказ, заработок/баланс.
- Shared: SOS (hold-ring, прерываемость — есть), навбар, кнопки, баннеры, honest-состояния (загрузка/ошибка/пусто).

### Флоу/интеграционные (Riverpod-провайдеры)
- order_flow: полный путь состояний; isLoading; ошибки; идемпотентный ключ сбрасывается при изменениях.
- Реакция на WebSocket-события (смена статуса заказа).

### Adversarial (frontend)
- Нет GPS/permission denied → честное состояние, не краш.
- Backend вернул ошибку/пусто → состояние ошибки + повтор, не выдуманные данные.
- Длинный адрес/кириллица → не ломает вёрстку (overflow ellipsis).
- Быстрые повторные тапы (двойной заказ, двойная оплата) → защита.

## Типы тестов и цели покрытия
| Область | Тип | Цель |
|---|---|---|
| Денежная логика (usecase/domain) | unit + property | ~100% ветвей |
| Репозитории (деньги/заказы/гонки) | integration (Postgres) | все критические пути |
| HTTP-слой | integration | все эндпоинты: 200/4xx/5xx |
| Стейт-машина | unit | все переходы (вкл. запрещённые) |
| Frontend виджеты | widget | все экраны, honest-состояния |
| Frontend флоу | provider/integration | ключевые пути |
| E2E | эмулятор | полный цикл заказа + диспетчеризация |
| Нагрузка | load (k6/vegeta) | пиковые эндпоинты |

## Принцип приёмки тестов
- Тест реально падает на баге и проходит на фиксе (не «зелёный ради зелёного»).
- Adversarial-кейсы обязательны, не только happy path.
- Я (техлид) проверяю каждый батч по коду: что тест бьёт по реальному сценарию, а не имитирует.
