# Авро — UI/UX релизный аудит

Дата начала: 2026-09-04
Цель: довести приложение до понятного, красивого и надёжного состояния перед релизом 30 сентября.

## Принцип аудита

Каждый экран проверяется не только как картинка, а как часть живого сценария:

- что пользователь хочет сделать;
- понятно ли, куда нажимать;
- красиво ли выглядят карточки, кнопки, отступы и текст;
- нет ли overflow, обрезаний, случайных модальных окон;
- есть ли loading/error/empty состояния;
- работает ли сценарий при слабом интернете, ошибке геолокации или отсутствии данных;
- совпадает ли экран с идеей бренда Авро: безопасность, спокойствие, помощь на дороге.

## Как включить галерею экранов на симуляторе

Для контролируемого просмотра без авторизации и реальных заказов запускаем
debug-сборку с флагом:

```bash
cd frontend
flutter run --dart-define=EVIK_UI_AUDIT=true
```

Выключить её можно явно через `--dart-define=EVIK_UI_AUDIT=false` или просто
не передавать флаг. В release-сборке флаг намеренно игнорируется: галерея не
может случайно попасть к пользователям.

## Подтверждённые UX-проблемы в сценарии эвакуатора

### UX-001 — два экрана для одного выбора

Маршрут клиента идёт `точка А → точка Б → /order/vehicle → поиск водителя`.
Экран `/order/vehicle` уже одновременно спрашивает тип автомобиля, колёса,
тип эвакуатора, комментарий и способ оплаты. При этом отдельный экран
`/order/tow-truck` также существует, предлагает те же типы эвакуатора и тоже
умеет запускать поиск. В живом сценарии он не вызывается.

Риск: у продукта два разных дизайна и две точки изменения цены/оплаты для
одного решения. Со временем они неизбежно разойдутся и пользователь получит
разные ответы в зависимости от входа.

Решение: оставить один экран. Для релиза лучше сделать `/order/vehicle`
единственным экраном «Детали заказа», а старый `/order/tow-truck` удалить из
маршрутизации после проверки, что на него нет внешних ссылок. В одном экране
должен быть явный порядок: 1) автомобиль, 2) состояние колёс, 3) подходящий
эвакуатор, 4) цена, 5) способ оплаты, 6) подтверждение.

### UX-002 — противоречивая подпись поля

На экране «Детали заказа» поле подписано «Тип эвакуатора», но выводит выбранный
тип автомобиля. Это вводит в заблуждение именно в момент заказа, когда ошибка
может означать неподходящую технику и потерянное время.

Решение: переименовать в «Ваш автомобиль» и показывать отдельный блок
«Подходящий эвакуатор» с кратким объяснением, почему он выбран.

### UX-003 — слабые состояния без данных

Экран информации о водителе при отсутствии водителя показывает только текст
«Информация о водителе недоступна», а трекинг — «Информация о заказе
недоступна». Для критичного заказа это выглядит как поломка, а не как честное
ожидание.

Решение: полноценные состояния: иконка, понятное объяснение, сохранённый
номер заказа, кнопка «Обновить», «Связаться с поддержкой» и, если заказ ещё
ищется, обратный переход к поиску.

### UX-004 — SOS пока является экраном экстренного звонка, а не центром безопасности

Сильные стороны уже есть: 112, полиция, скорая, копирование координат и работа
с последней GPS-точкой. Но на экране нет статуса доставки SOS-события, времени
последней координаты, заряда/сети, доверенных контактов, подтверждения отправки
в поддержку и понятного «что делать сейчас».

Решение: построить SOS как отдельный сценарий: большая красная кнопка
«Отправить SOS», затем экран статуса «событие отправлено / нет сети, координаты
сохранены локально», контакт 112, отправка координат, поддержка, близкие люди.
Это должно быть ядром бренда Авро, а не вторичной страницей приложения.

## Визуальный уровень «как команда дизайнеров»

1. Один дизайн-язык: фиксированная сетка 8 px, три уровня текста, одинаковые
   радиусы, тени и состояния кнопок на всех клиентских и водительских экранах.
2. Одна главная задача на каждом экране. Сейчас на экране деталей заказа
   слишком много равнозначных блоков; цена и действие должны быть постоянно
   видны внизу, а детали — раскрываемыми.
3. Карта должна не быть серым фоном: маршрут, точки А/Б, ETA, водитель и зона
   обслуживания визуально важнее декоративных карточек.
4. У водителя главный экран должен показывать контекст работы: «в сети», зона,
   спрос, заработок сегодня и одну большую кнопку следующего действия. Экран
   активного заказа уже ближе к этому уровню: карта + статус + сумма + CTA.
5. Все пустые, загрузочные и ошибочные состояния должны выглядеть как часть
   бренда, а не как технический текст по центру экрана.

## Решение по приоритетам

До релиза нельзя распыляться на все партнёрские услуги как полноценный маркетплейс. Для 30 сентября главный фокус:

1. Эвакуатор end-to-end.
2. SOS.
3. Админка владельца под эвакуатор и SOS.
4. Безопасность, платежи, зоны, push, карты.
