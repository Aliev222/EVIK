# Точка Банк — Cyclops («Расчёты по номинальному счёту»)

> Исследование платёжной модели для будущей интеграции выплат водителям Авро.
> Дата: 2026-08-08. Статус: справочный документ, интеграция НЕ начата (блокеры ниже).
> Все факты собраны из официальной документации Точка Банка (источники в конце файла).

## Зачем этот документ

Расул хочет выплачивать водителям через Точка Банк (сервис Cyclops), а не через
ЮKassa. В текущем коде выплаты завязаны на ЮKassa (`yookassa_client.go`), причём
live-режим payout там не реализован (только sandbox-заглушка). Cyclops —
принципиально другая модель (номинальный счёт + сплит через сделки), которая
хорошо ложится на схему «клиент платит → платформа берёт комиссию 15% →
водитель-самозанятый получает остаток».

## Что такое Cyclops

Официальное название — **«Расчёты по номинальному счёту»**. Это инструмент для
маркетплейсов/платформ, а не обычный эквайринг.

Ключевые сущности:

- **Площадка (система)** — Авро, владелец номинального счёта.
- **Номинальный счёт** — один общий счёт, куда падают деньги клиентов. Юридически
  эти деньги не принадлежат площадке (важно для налогов — не считаются доходом
  Авро).
- **Бенефициар** — водитель (регистрируется через `create_beneficiary_fl` с ИНН,
  паспортом, ФИО).
- **Виртуальный счёт** — «кошелёк» водителя внутри номинального счёта. Хранит
  баланс: доступные и заблокированные средства. Тип `standard` (основной),
  `for_ndfl` (накопление на налоги).
- **Сделка (deal)** — сущность, где указано кто платит и кто получает; здесь и
  происходит сплит суммы.

## Основной бизнес-процесс (полный цикл одного заказа)

1. **Клиент пополняет номинальный счёт** — по реквизитам, через QR-код СБП
   (`generate_sbp_qrcode`) или через интернет-эквайринг Точки.
2. **Регистрация бенефициара** (если водитель ещё не заведён) —
   `create_beneficiary_fl` + загрузка договора оферты (`contract_offer`).
3. **Создание виртуального счёта** — `create_virtual_account` (тип `standard`).
4. **Идентификация платежа** — `identification_payment`. Площадка сообщает банку,
   какому водителю принадлежит входящий платёж. Деньги зачисляются на виртуальный
   счёт водителя.
   - ⚠️ **Лимит 96 часов** на идентификацию, иначе банк авто-вернёт деньги клиенту
     (на тесте — 30 минут). Это ограничение ТОЛЬКО на шаг идентификации, а НЕ на
     то, сколько деньги могут лежать на балансе водителя. После идентификации
     деньги на виртуальном счёте лежат сколько угодно.
5. **Создание сделки** — `create_deal`. Здесь происходит СПЛИТ:
   - `payers` — виртуальный счёт водителя и сумма (блокируется).
   - `recipients` — получатели:
     - `commission` — комиссия площадки (15% Авро) → на расчётный счёт площадки.
     - `payment_contract` / `payment_contract_by_sbp` / `payment_contract_to_card`
       — доля водителя (85%) по его реквизитам / СБП / на карту.
     - `ndfl_to_virtual_account` — отчисление на налоговый счёт `for_ndfl`
       (для самозанятых).
   - К сделке нужно приложить документ (`service_agreement`) для каждого плательщика.
6. **Исполнение сделки** — `execute_deal`. Банк формирует реальные платёжные
   поручения и отправляет деньги получателям.

**Важно:** сплит делается НЕ в момент оплаты клиентом, а отдельным шагом (сделкой),
где backend Авро явно раскладывает сумму на «комиссию» и «долю водителя».

## Налоги самозанятых

Тип получателя `ndfl_to_virtual_account` + счёт `for_ndfl` позволяют автоматически
откладывать часть на налоги водителя и потом платить в ФНС через
`payment_of_taxes`. Прямо закрывает агентскую схему с самозанятыми.

## Технические требования (влияют на архитектуру Авро)

- **JSON-RPC API**, каждый запрос **криптографически подписывается**:
  - RSA-ключ через OpenSSL, ИЛИ ГОСТ-2012 через КриптоПро.
  - Заголовки: `sign-data` (подпись тела, sha256), `sign-thumbprint` (отпечаток
    ключа), `sign-system` (идентификатор площадки).
  - Приватный ключ живёт ТОЛЬКО на backend. Никогда во Flutter (совпадает с
    правилом Авро про секреты).
- **Доступ по фиксированным IP** — нужно заранее сообщить банку адреса, с которых
  пойдут запросы. → отсюда блокер «миграция на VPS для статического IP».
- **Два слоя:**
  - Тест: `https://pre.tochka.com/api/v1/cyclops`
  - Прод: `https://api.tochka.com/api/v1/cyclops`
- **Подключение:** письмо на `public-api@tochka.com`, нужен зарегистрированный
  ИП/юрлицо.

## График проведения платежей (для UX ожиданий)

- Платежи по реквизитам: будни 01:10–19:50, воскресенье ограниченно.
- Внутри Точка Банка: 24×7, мгновенно.
- По номеру карты: 24×7, обычно до 2 минут (макс 1 час).
- По СБП (номер телефона): 24×7, до 5 минут (старый способ — до 1,5 часов).

## Что это значит для архитектуры Авро — РАЗВИЛКА (нужен ADR)

Сейчас `driver_wallets` — внутренний ledger Авро в своей БД. Cyclops предлагает
сделать банк источником истины по балансу водителя через виртуальные счета.

Два варианта (решить отдельным архитектурным решением, когда снимутся блокеры):

- **Вариант 1 — банк = источник истины.** Виртуальный счёт Cyclops и есть баланс
  водителя; `driver_wallets` становится кешем/зеркалом. Даёт «реальный баланс из
  банка» в приложении (`get_virtual_account`). Требует переписать учёт денег.
- **Вариант 2 — наш ledger = истина.** `driver_wallets` остаётся истиной, Cyclops
  дёргается только на выплату. Меньше переписывания, но баланс в приложении —
  по-прежнему внутренний расчёт, не банковский.

## Автосоздание бенефициара

Заводить бенефициара + виртуальный счёт нужно автоматически — но НЕ при первом
входе, а **в момент одобрения модерации водителя** (когда уже есть проверенные
паспорт/ИНН, которые Cyclops валидирует). Схема:

1. Модерация approve → запись в БД, что водитель approved.
2. Отдельным фоновым шагом (очередь/ретраи) → `create_beneficiary_fl` +
   `create_virtual_account` в Cyclops. Идемпотентно, с повторами при сбое банка.
3. Сохранить у себя маппинг `driver_id → beneficiary_id → virtual_account_id`.
4. Готовность к деньгам = «модерация пройдена И виртуальный счёт создан».

Падение вызова к банку не должно ломать регистрацию водителя.

## Нужен фоновый обработчик платежей

Backend должен регулярно (напр. раз в минуту) дёргать `list_payments` с фильтром
`identify: false`, находить новые неопознанные платежи и сразу идентифицировать их
к нужному водителю — чтобы никогда не задеть 96-часовой лимит. Тот же паттерн
«reaper», что нужен для возвратов (дыра №2).

## Блокеры (почему интеграция НЕ начата)

- Регистрация ИП (нужна для договора с банком).
- Статический IP → миграция на VPS (Cyclops пускает только с согласованных IP).
- Доступ от банка: письмо на `public-api@tochka.com`.
- Не кодовые задачи — организационные.

## Минимальный набор API-методов для MVP выплат

- `create_beneficiary_fl` — регистрация водителя.
- `upload_document/beneficiary` — договор оферты.
- `create_virtual_account` — кошелёк водителя.
- `list_payments` (`identify: false`) — поиск входящих платежей.
- `identification_payment` — привязка платежа к водителю.
- `create_deal` + `upload_document/deal` — сделка со сплитом (комиссия + водитель).
- `execute_deal` — исполнение выплат.
- `get_virtual_account` — баланс водителя (если банк = источник истины).
- (опц.) `payment_of_taxes`, `ndfl_to_virtual_account` — налоги самозанятых.
